Which code sandbox should your AI agent use? 5 options compared

This page is for a remote computer where an agent runs code: a shell, a filesystem, packages, and sometimes a desktop or a GPU. The sandbox built into a coding agent on your laptop is a different control, covered in the safety guide. Clicking through a website is a third job, covered in the browser automation guide. The five tools below are hosted sandboxes. They split on whether you reserve the machine, pay for the CPU you actually burn, or already sit on that vendor's app platform. We checked every price and free tier on the vendor's own pages on November 4, 2026. Where two of those pages disagree, the tool section quotes both.

Four jobs, four bills

Before you compare the hourly rate, decide what the sandbox has to be:

  • A Linux machine for a coding agent. The agent installs packages, edits a repo, and runs tests. E2B, Daytona, Modal, Cloudflare's container sandboxes, and Vercel Sandbox all do this. The coding-agents guide is about which agent you point at that machine.
  • A short snippet with a result. You want runCode() or one command, then the box can go away. E2B's Code Interpreter SDK, Modal's exec, and Cloudflare Dynamic Workers (JavaScript, Python, or WebAssembly) are built for that shape. Dynamic Workers are an isolate, so they are the wrong box when the job needs apt, a compiler, or a long-running process.
  • A bill that matches waiting. Agents spend a lot of wall-clock time blocked on a model. E2B and Daytona reserve vCPU and RAM and bill that reservation while the sandbox is running. Modal bills the higher of what you requested and what the sandbox used, with a small default request. Vercel bills Active CPU only while the CPU is busy, and bills memory for the whole session. Cloudflare Containers bill CPU on active use and memory and disk on the instance size until the container sleeps.
  • A call from the coding agent you already have. Daytona, Vercel, and Cloudflare document an MCP server that can drive their sandboxes. E2B's documented MCP is a gateway that runs other tools inside the sandbox. Modal's docs show how to host an MCP server you write. Adding any of those servers is covered in the MCP setup guide.

The model that decides each command is a separate bill. Estimate it with the AI API cost calculator.

Tool by tool

Prices are in US dollars, from each vendor's own page on November 4, 2026. Per-hour figures we calculated from a published per-second rate are labeled as calculated.

E2B

Type · free tier: Hosted Linux microVM for agents · Hobby is $0, with a one-time $100 usage credit, no card

  • What it is: isolated Linux machines an agent can drive with the Python or JavaScript SDK (pip install e2b on Python 3.10+, or npm install e2b on Node.js 20.18.1+ or 22+). The docs describe a sandbox as a Linux VM you can pause and resume. The open-source page says each session is a Firecracker microVM with its own kernel. Sandbox.create() with no template uses the Debian base image, which includes Python 3, Node.js, Yarn, git, curl, build-essential, and the GitHub CLI. A separate Code Interpreter package adds runCode() / run_code() and can return charts, tables, and images. E2B also publishes a desktop stack for a graphical Linux session. The pricing page says sandboxes are CPU-only. Secrets can live outside the sandbox: the secrets docs say the egress proxy injects the current value into matching outbound HTTPS requests, and the sandbox configuration stores a reference.
  • When to pick it: the agent needs a Linux computer you can pause between turns, and you want the runtime's source public. Pick Daytona when you need Windows, macOS, or a GPU. Pick Modal when the process is bursty and a reserved 2 vCPU would sit idle.
  • Open source: Apache-2.0 on e2b-dev/E2B, e2b-dev/runtime, and e2b-dev/code-interpreter, from the GitHub license API on November 4, 2026. Those repos had 14,710, 1,809, and 2,427 stars that day. The open-source page says the public stack includes the SDKs, CLI, runtime, control plane, and Firecracker layer, and that E2B Embed runs it on one Linux machine with KVM. The same page reports more than 25,000 stars across the organization's repositories. BYOC runs the data plane in your AWS, GCP, or Azure account.
  • Pricing: you pay per second for allocated vCPU and RAM while the sandbox is running. Paused, killed, and timed-out sandboxes stop compute billing immediately. Disk is included. The pricing page and the price FAQ both list $0.000014 per vCPU-second ($0.0504 per vCPU-hour) and $0.0000045 per GiB-second ($0.0162 per GiB-hour).
    • Hobby: $0 a month, $100 of credits once, 20 concurrent running sandboxes, 1 hour of continuous runtime, 10 GiB disk, 20 concurrent template builds, 1 sandbox create per second, 10 secrets per project. Paused sandboxes are kept with no time limit. No card. When the credits are gone and there is no payment method, the billing FAQ says every project in the workspace is blocked.
    • Pro: $150 a month plus usage, and no extra credits. 100 concurrent sandboxes, 24 hours of continuous runtime, 20 GiB disk, 5 creates per second, 100 secrets. CPU and memory can go above the Hobby ceiling of 8 vCPU and 8 GiB by contacting support.
    • Concurrency add-ons, from the pricing page: Pro+ is $650 a month for 600 concurrent sandboxes, and Pro++ is $1,150 a month for 1,100. The billing page describes the same ceiling as add-ons of 500 slots for $500 a month. Usage is extra.
    • Enterprise: the pricing page says a $3,000 monthly minimum applies. The billing page calls Enterprise pricing custom, with concurrency above 1,100.
  • MCP: an MCP gateway runs inside the sandbox. The docs say it can expose 200+ servers from the Docker MCP Catalog, plus a custom server cloned from a public GitHub repo. From outside, you use getMcpUrl() and a bearer token. Inside the sandbox the gateway is at http://localhost:50005/mcp. That is a gateway for tools in the sandbox. We did not find a hosted E2B MCP server whose job is creating sandboxes from Cursor.
  • Downsides: two official pages disagree on the default size, and the hourly bill moves with it. The base-image doc says a sandbox built from base starts at 2 vCPU and 512 MiB. The price FAQ uses that size and works an hour out to about $0.109 (2 × $0.0504 + 0.5 × $0.0162). The pricing page says the default sandbox has 2 vCPUs and 4 GiB of RAM. At the same published rates, 4 GiB is 2 × $0.0504 + 4 × $0.0162 = $0.1656 an hour. The build-limits page says a template rebuild that omits CPU and memory writes 2 vCPU and 1024 MiB. Read getInfo() on a sandbox you just created before you budget a fleet. Hobby sessions end at one hour unless you pause, and pausing is what resets that clock. There is no GPU. Pro's $150 does not include more credits.

Our take: The default hosted Linux machine when you want to pause it and keep the filesystem and memory. Call pause() when the agent is waiting on you. Move to Pro when a session needs to stay up past an hour or you need more than 20 at once.

Daytona

Type · free tier: Hosted sandboxes for AI-generated code · $200 of compute credit, no card

  • What it is: programmable computers for agents. The sandboxes doc says each one gets a dedicated kernel, filesystem, network stack, and allocated vCPU, RAM, and disk. The default class is a Linux container. The same page also offers a Linux VM, Windows, GPU sandboxes (NVIDIA and AMD), and macOS on Apple silicon. The sandboxes page marks the default container runtime at under 90ms. SDKs are Python, TypeScript, Ruby, Go, and Java, plus a CLI. Direct code execution defaults to Python. A new sandbox is 1 vCPU, 1 GiB RAM, and 3 GiB disk. The sandboxes page caps a sandbox at 4 vCPU, 8 GiB RAM, and 10 GiB disk.
  • When to pick it: the agent needs a desktop OS, a GPU, or a container you can archive so disk billing stops. The $200 credit is the largest published starting balance in this guide. E2B is the closer match when you want the isolation layer's source and you can stay on CPU Linux.
  • Open source: Daytona's June 11, 2026 post says the production codebase moved to closed source, and the old public repo stays up without further updates. On November 4, 2026, daytonaio/daytona was archived (71,383 stars). Its README says it is unmaintained as of June 2026 and points the license at tag v0.190.0, which is AGPL-3.0. The current clients repo, daytona/clients, had 16 stars. Its LICENSE file says the cli/ directory is AGPL-3.0 and the rest is Apache-2.0. The GitHub license API returns no SPDX id for that split. You can read the SDKs and the CLI. You cannot read the current sandbox runtime.
  • Pricing: pay as you go, calculated per second, for resources reserved. The pricing page lists compute at $0.0504 per vCPU-hour, memory at $0.0162 per GiB-hour, and storage at $0.000108 per GiB-hour after the first 5 GiB, which the footnote marks free. It does not say whether those 5 GiB are per sandbox or per organization. A default 1 vCPU and 1 GiB sandbox is $0.0504 + $0.0162 = $0.0666 an hour while it is started, before disk. The same page lists Windows at $0.0858 per vCPU-hour and does not say whether that replaces the Linux vCPU rate. Stopped and paused sandboxes bill disk only. The billing page says preserved memory on pause is not billed, pause is for VM sandboxes, and archive (containers only) stops billing. Ephemeral sandboxes and GPU sandboxes are deleted when they stop, so they have no stopped-disk charge. Deleted sandboxes are not billed. Snapshots you created still are.
    • Free credit: $200 of compute, no card. The billing page says the free credit balance is not available for GPU sandboxes. Daytona spends free credits before paid ones.
    • Tiers, from the limits page: email verification puts you on Tier 1. The Limits table lists Tier 1 as 10 vCPU, 20 GiB memory, and 30 GiB storage, with 10,000 general requests a minute and 300 sandbox creates a minute. The Tiers table on that same page lists Tier 1 RAM as 10 GiB. Tier 2 needs a card and a $25 top-up (100 vCPU / 200 GiB / 300 GiB). Tier 3 needs a $500 top-up. Tier 4 needs a $2,000 top-up every 30 days. GPU vCPU, memory, and disk sit in a separate quota. Spot GPUs require Tier 2 or higher.
    • Preemptible GPUs, per hour on the pricing page: B300 $4.08, B200 $3.59, AMD MI355X $3.44, H200 $2.61, H100 $2.27, RTX PRO 6000 $1.74, RTX 5090 $0.74, RTX 4090 $0.57. The page also has an on-demand GPU view. Those dollar rates were not in the page text we could read, so they are left out here.
    • Startups: the pricing page says Daytona supports startups with up to $50,000 in credits. Enterprise is the path for larger limits, SSO, audit logs, or BYOC. Volume discounts are mentioned, with no public percentage table.
    • Lifecycle: if you do not set it, auto-stop is 15 minutes, and the docs say it fires even when processes are still running. VM sandboxes that support pause default to a 60-minute auto-pause when you set neither auto-pause nor auto-stop.
  • MCP: the CLI is the server. daytona mcp init supports Claude, Cursor, and Windsurf. daytona mcp start runs it. The docs list sandbox management, file operations, git, process and code execution, computer use, and preview.
  • Downsides: a running sandbox bills the reservation, including time the agent spends waiting. Stopping a normal container does not zero the bill. Disk continues until you archive it. The default auto-stop at 15 minutes will cut off a long agent unless you set the interval to 0. Tier 1's pool is 10 vCPU, and the two tables on the limits page disagree on whether Tier 1 RAM is 10 or 20 GiB. Free credits do not pay for GPUs. macOS sandboxes are documented, and we did not find a separate public macOS price. The production runtime is private, so you cannot audit the isolation boundary the way you can with E2B.

Our take: The pick when the agent needs Windows, a GPU, or macOS, and when a $200 credit is enough to learn the API. Archive containers you have stopped. For a CPU Linux coding agent and a public runtime, E2B is the simpler default.

Modal Sandboxes

Type · free tier: Elastic containers for untrusted code · Starter is $0, with $30 of compute credit a month

  • What it is: Modal's sandbox API, separate from Modal Functions. You create a sandbox on an app and run commands with exec. The guide describes them as secure containers for code from a model, a test suite, or a repo checkout. Python, JavaScript, and Go clients are in the docs. CPU sandboxes are not preempted. GPU sandboxes are preemptible and require runtime="gvisor". The products page says sandboxes start in under a second, including on custom images, and that Modal has tested scheduling past one million concurrent sandboxes. Starter concurrency is still the plan cap below.
  • When to pick it: the work comes in spikes, and you would rather pay for CPU and memory the sandbox actually uses than for a size you reserved up front. Also the pick when the same account should run GPU sandboxes and the rest of a Modal app. A coding agent that sits at a reserved 2 vCPU for a long session is often cheaper on E2B or Daytona at the rates below.
  • Open source: modal-labs/modal-client is Apache-2.0, from the GitHub license API on November 4, 2026 (532 stars). That repo is the SDK. We did not find a public repo for the sandbox hosts.
  • Pricing: Sandboxes bill max(request, actual) per second, at the non-preemptible rate, which the pricing page states as 3× the Function list price. The sandbox block lists CPU at $0.00003942 per physical-core-second and memory at $0.00000667 per GiB-second. The products page prints the same CPU rate as $0.1419 per core-hour and memory as $0.0240 per GiB-hour. One physical core is 2 vCPUs. The minimum request is 0.125 cores and 128 MiB. At those hourly rates, a sandbox that stays on the default request costs 0.125 × $0.1419 + 0.125 × $0.0240 = $0.0207375 an hour. Bursting above the request bills the higher use for that second. The pricing FAQ says to estimate from average use, because peak use overstates a bursty sandbox.
    • Starter: $0 a month, $30 of compute credit a month, 3 seats, 100 containers, 10 GPU concurrency, 1 TiB of egress, 1 day of logs, 200 deployed apps, 5 crons. The sandbox FAQ says that container cap is the concurrency limit. Credits cover Functions and Sandboxes (CPU, memory, GPU). The pricing FAQ says they do not cover Shared Endpoints, which have billed tokens from the first request since September 1, 2026. Volumes include 1 TiB and then $0.09 per GiB-month. Region selection is listed at 1.15–1.75× base prices.
    • Team: $250 a month, $100 of compute credit, unlimited seats, 5,000 containers, 50 GPU concurrency, 10 TiB of egress, 30-day logs, custom domains, static IP proxy, RBAC, and environment budgets.
    • Enterprise: custom credits, concurrency, HIPAA, audit logs, and SSO.
    • Lifetime: the sandboxes guide says the default maximum is 5 minutes (the Python SDK parameter defaults to 300 seconds) and you can set a timeout up to 24 hours. Longer work uses a filesystem snapshot and a new sandbox. An idle timeout can stop a sandbox that has no running command, no stdin writes, and no open tunnel. On the VM runtime the root filesystem is a fixed 512 GiB and cannot be increased. The sandbox pricing section does not list a separate disk rate. Its GPU heading did not include a rate table in the page text we read. GPU sandboxes are preemptible, so this guide does not apply the 3× CPU multiplier to them.
  • MCP: Modal's docs include an example that deploys a stateless MCP server you write as a web Function, and an example that runs Claude Code inside a sandbox. We did not find a Modal-hosted MCP server for creating sandboxes.
  • Downsides: the default 5-minute lifetime ends a coding session unless you raise the timeout. CPU is billed in physical cores, so a "2 vCPU" comparison with E2B or Daytona is one Modal core at $0.1419 an hour if that core is requested or used the whole time, before memory. That is well above E2B and Daytona's $0.0504 per vCPU-hour when the machine stays busy. The $30 credit is monthly, and anything past it bills on Starter even though the plan fee is $0. GPU work can be preempted. A sandbox that bursts without a limit can run the bill up. The docs say to set a CPU and memory limit when an agent controls the process.

Our take: The sandbox to use when most seconds are idle or bursty, and when you will leave the request at the default until metrics say otherwise. Set a limit before an agent can install the world. For a reserved Linux machine that pauses, start with E2B.

Cloudflare Sandboxes

Type · free tier: Sandboxes on Cloudflare Workers · no free sandbox; Workers Paid is required

  • What it is: two environments, both reached from a Worker. Containers run an image you provide as a Linux microVM with its own kernel and network. The overview says a sandbox container uses the Durable Object scheduling policy, which is in public beta. @cloudflare/sandbox adds file helpers on top of the container API. The package README says a sandbox is a Durable Object plus the container it starts. Dynamic Workers load untrusted JavaScript, Python, or WebAssembly as a separate Worker. You compile TypeScript first. The docs tell apps still on @cloudflare/sandbox 0.x to use the legacy Sandbox SDK pages or migrate. The current overview was last updated September 30, 2026.
  • When to pick it: the product is already a Worker, and the agent should run code beside it. Use a container when the job needs a Linux userland, a package manager, or a process that stays up. Use a Dynamic Worker when the code is a module you can call and you want outbound network blocked unless you pass it. A long-lived multi-language devbox with a published pause price is a better fit for E2B or Vercel.
  • Open source: packages/sandbox/LICENSE in cloudflare/sandbox-sdk is Apache-2.0. We read that file on November 4, 2026. The repo had 1,159 stars. GitHub's license API reports no SPDX id, because the root LICENSE file only points at the package license. The Workers and Containers platforms are Cloudflare's service.
  • Pricing: there is no sandbox on the Workers Free plan. Containers pricing says the Free column is not available, and Dynamic Workers pricing says they are only on Workers Paid. Workers Paid has a $5 monthly minimum. Workers pricing was last updated October 2, 2026.
    • Linux containers, from the Containers pricing page, included each month on Workers Paid, then overage: 25 GiB-hours of memory, then $0.0000025 per GiB-second; 375 vCPU-minutes of CPU, then $0.000020 per vCPU-second; 200 GB-hours of disk, then $0.00000007 per GB-second. Calculated from those per-second rates, extra CPU is $0.072 per active vCPU-hour, extra memory is $0.009 per GiB-hour, and extra disk is $0.000252 per GB-hour. CPU is active use. Memory and disk are the instance size you selected. Billing starts when a request hits the container or you start it, and stops when the instance sleeps.
    • Instance types: lite (1/16 vCPU, 256 MiB, 2 GB disk), basic (1/4 vCPU, 1 GiB, 4 GB), standard-1 (1/2 vCPU, 4 GiB, 8 GB), standard-2 (1 vCPU, 6 GiB, 12 GB), standard-3 (2 vCPU, 8 GiB, 16 GB), standard-4 (4 vCPU, 12 GiB, 20 GB).
    • Container egress: $0.025 per GB in North America and Europe (1 TB included), $0.05 in Oceania, Korea, and Taiwan (500 GB), and $0.04 elsewhere (500 GB). Each container also has a Durable Object. On Workers Paid, Durable Objects include 1 million requests and 400,000 GB-seconds a month, then $0.15 per million requests and $12.50 per million GB-seconds.
    • Dynamic Workers: 1,000 unique workers a month, then $0.002 per Dynamic Worker per day. The pricing page says that daily charge has been billed since May 26, 2026. Requests and CPU time use Workers Standard rates and count toward the Workers bill: 10 million requests and 30 million CPU milliseconds included, then $0.30 per million requests and $0.02 per million CPU milliseconds. Dynamic Workers bill startup CPU as well as execution CPU, and they exclude I/O wait. A call with no stable id counts as a new worker every time.
  • MCP: Cloudflare's MCP catalog, updated October 27, 2026, lists a Container server at https://containers.mcp.cloudflare.com/mcp described as spinning up a sandbox development environment. The API server at https://mcp.cloudflare.com/mcp covers the Cloudflare API with OAuth. We did not enumerate every tool on the Container server.
  • Downsides: the $5 plan is the entry fee, and a Linux sandbox can bill Containers, Durable Objects, and Workers on the same session. The largest published instance is 4 vCPU and 12 GiB, which is a small coding machine. The overview says the Durable Object scheduling policy used by a sandbox container is in public beta. Dynamic Workers are the wrong tool for apt, Docker, or a language runtime you install yourself. There is no published GPU sandbox.

Our take: The sandbox to use when the caller is already a Worker. Pick a container for a real Linux session and a Dynamic Worker for a function you can call with the network off. Keep a stable Dynamic Worker id so each retry is not a new daily charge.

Vercel Sandbox

Type · free tier: Isolated Linux microVM · Hobby is $0 inside the quotas below

  • What it is: Firecracker microVMs for untrusted or agent-generated code. The docs say each sandbox has its own filesystem and network. The default image is vercel/sandbox/universal, with the current Node.js LTS, Python 3.14, coding agents, and common utilities. You can also use Ubuntu, Arch, another Linux image, or your own OCI image. Persistence is the default: a sandbox saves state on stop and resumes later. SDKs are @vercel/sandbox and vercel.sandbox in the Python package, plus a sandbox CLI. Auth is a Vercel OIDC token, or an access token off Vercel. The SDK reference includes networkPolicy: 'deny-all'.
  • When to pick it: the agent spends most of a session waiting on a model or an API, and you want CPU charges to follow busy time. Also the pick when the app already deploys on Vercel and you want the sandbox, snapshots, and drives on that account. A fully busy reserved machine is easier to price on E2B or Daytona.
  • Open source: vercel/sandbox is Apache-2.0, from the GitHub license API on November 4, 2026 (219 stars). The repo is the SDK and CLI. The microVMs run on Vercel.
  • Pricing: Hobby is $0 a month on vercel.com/pricing. Pro is $20 a month. The sandbox pricing page says Pro sandbox usage is charged against your $20 a month credit, then at the rates below. Rates in the sandbox table for Active CPU, memory, data transfer, and drives are the default iad1 region. Other regions differ, and the page loads those rates in a selector, so this guide does not copy them. Creations and snapshot storage are the same in every region where Sandbox is available. The main pricing page lists the Pro CPU and memory rates as "starting at" the same figures, which matches a regional floor.
    • Hobby included each month: 5 active CPU hours, 420 GB-hours of memory, 5,000 creations, 20 GB of data transfer, 10 concurrent sandboxes, sessions up to 45 minutes. Snapshot storage and drive storage are 15 GB each, for the lifetime of the account rather than per month. Drive reads and writes are 30 GB each. vCPU allocation starts at 20 per minute and can ramp to 40. Max size is 4 vCPU and 8 GB of memory. Past the quota, the pricing page says you are not charged. One sentence says creation pauses until the next billing cycle. Another says it pauses until 30 days after you first used the feature. Both are on that page.
    • Pro, iad1: Active CPU $0.128 per hour, provisioned memory $0.0212 per GB-hour, creations $0.60 per million, data transfer included in the flat-rate CDN, snapshots $0.08 per GB-month, drive storage $0.05 per GB-month, drive reads $0.0015 per GB, drive writes $0.004 per GB. 10,000 concurrent sandboxes, sessions up to 24 hours, max 8 vCPU and 16 GB. Allocation starts at 150 vCPU per minute and ramps by 500 a minute up to 5,000.
    • Active CPU is time the code uses the CPU, summed across vCPUs. Waiting on network, a database, or a model does not count. Memory is allocated size times running time, billed in 1-minute minimums, including idle time. Each vCPU includes 2 GB of memory. The default is 2 vCPUs. Downloads from the internet are free. Data the sandbox sends, and traffic through exposed ports, is billable.
    • Vercel's own iad1 examples, at 10% CPU to reflect model waits: a 5-minute, 2 vCPU, 4 GB run is $0.0021 of CPU and $0.0071 of memory, $0.0092 together. Their overview example for 1 vCPU and 2 GB running all day is $1.05 idle at 1% CPU ($31.45 over 30 days), $4.09 if that vCPU stays busy ($122.69 over 30 days), and $0 when the sandbox is stopped.
    • Enterprise: vercel.com/pricing lists sandbox CPU, memory, creations, transfer, concurrency, and snapshots as custom. The sandbox pricing page prints the same iad1 rates as Pro in the Enterprise column, says Enterprise plans have custom pricing and quotas, and lists a resource cap of 32 vCPU and 64 GB. Treat the public Pro rates as the published iad1 list, and ask sales before you budget Enterprise.
    • Other limits: default timeout is 5 minutes, and you extend it in code up to the plan maximum. SDK 3.0.0 and later, and custom images, get 64 GB of ephemeral NVMe. Older runtimes get 32 GB. Snapshots expire 30 days after their last use unless you change that. A sandbox can mount up to 4 drives. A drive you do not size defaults to 1 TiB, or 1 GiB on Hobby.
  • MCP: Vercel MCP is a remote server at https://mcp.vercel.com with OAuth, on all plans. The docs say it follows MCP authorization and Streamable HTTP, and the sandbox tool pages cover creating sandboxes, running commands, and snapshots. The install line in the docs is npx add-mcp https://mcp.vercel.com. Connecting grants the agent the same access as your Vercel user.
  • Downsides: memory keeps billing for the whole session, so an "idle" agent is not free. Vercel's own 1 vCPU, 2 GB idle day is $1.05. Which Hobby quota runs out first depends on CPU use. A default 2 vCPU sandbox provisions 4 GB, so 420 GB-hours is 105 hours of wall-clock memory. At full CPU that sandbox spends 2 active CPU hours per wall-clock hour, so the 5-hour CPU quota arrives after 2.5 hours. At 1% CPU, the memory quota is the one that runs out. The two Hobby pause sentences disagree. Regional rates are not in the static page. Enterprise is custom on the main pricing page even though the sandbox table prints Pro's numbers in that column. The default 5-minute timeout will kill a first run unless you extend it.

Our take: The sandbox to use when the agent is mostly waiting and you will stop it between tasks. Stay on Hobby until the 5 CPU hours or the memory quota runs out. On Pro, sandbox usage draws down the $20 monthly credit before those rates apply.

Picks by use case (our take)

  • A Linux machine you can pause: E2B Hobby. One-time $100 credit, and compute billing stops on pause. Read the live CPU and RAM with getInfo() before you trust either default-size page.
  • Windows, a GPU, or macOS: Daytona. Budget GPU time with paid credit. The $200 free credit does not apply to GPU sandboxes.
  • Short, bursty runs and evals: Modal Sandboxes, left on the default 0.125 core and 128 MiB request, with a CPU and memory limit set.
  • The caller is already a Cloudflare Worker: Cloudflare Sandboxes. A container for Linux, a Dynamic Worker for a module with the network off.
  • The agent waits on a model: Vercel Sandbox. Active CPU skips that wait. Stop the sandbox when the turn is over so memory stops too.
  • Run the stack yourself: E2B Embed, Apache-2.0, on one Linux machine with KVM. Daytona's old public repo is AGPL-3.0 and archived.
  • The sandbox is the coding agent on your laptop: the safety guide. That is approval modes and a local sandbox, not one of these hosts.
  • Click, type, and log in on a website: the browser automation guide. A full Linux VM is the wrong bill for that.

Before you run the code

  • Keep the agent's laptop sandbox on too. A remote machine limits what generated code can do to your files. It does not replace the approval mode of the coding agent that is allowed to call the API. Start with the safety guide.
  • Assume command output is untrusted. A repo the agent clones can contain instructions aimed at the model. Keep a human check on anything that can pay, send, or delete. See the MCP setup guide.
  • Keep production secrets out of the sandbox. E2B's secrets docs store the value outside the sandbox and inject it, on matching HTTPS requests, at the egress proxy. Modal can block network or allowlist domains. Vercel's SDK can start with networkPolicy: 'deny-all'. Cloudflare's container example sets enableInternet: false, and the Dynamic Workers example sets globalOutbound: null.
  • Stop the meter when the turn ends. E2B: pause() or kill(). Daytona: archive a stopped container, or disk keeps billing. Modal: terminate(), or the timeout will, at 5 minutes unless you changed it. Vercel: sandbox.stop(), or memory keeps billing. Cloudflare: let the container sleep, and use a stable id for Dynamic Workers.
  • Cap the account. E2B has a budget page. Modal has a workspace budget. Vercel has Spend Management on Pro. Daytona's wallet can top up automatically, which will spend a card if the $200 credit runs out.
  • Read the page that disagrees with the one you priced from. E2B's default RAM, Daytona's Tier 1 RAM, and Vercel's Hobby reset wording and Enterprise column are all inconsistent across official pages as of November 4, 2026. The source links are the check, not this summary.

FAQ

What's the best code sandbox for AI agents?

It depends on the job. For a Linux microVM you can pause, start with E2B Hobby. For Windows, a GPU, or macOS, use Daytona. For short bursts that should not reserve a large machine, use Modal Sandboxes. If the app already runs on Cloudflare Workers, use Cloudflare Sandboxes. If the agent spends most of its time waiting on a model, use Vercel Sandbox.

How is this different from sandboxing a coding agent on my laptop?

This page compares hosted computers where an agent runs code, installs packages, and keeps files. The safety guide covers folder choice, approval modes, and the sandbox built into Claude Code, Cursor, Codex, and the other coding agents on your own machine: https://hotfixdaily.com/guides/run-ai-coding-agents-safely/. Clicking through a website is covered in the browser automation guide.

E2B or Daytona?

Both bill reserved vCPU and memory by the second while a sandbox is running, and both publish $0.0504 per vCPU-hour and $0.0162 per GiB-hour. E2B includes disk and has no GPU. Daytona also bills disk and offers Windows, GPU, and macOS. E2B Hobby includes a one-time $100 credit. Daytona includes $200 of compute credit. E2B's runtime is Apache-2.0. Daytona's current production code is private.

Which sandboxes bill me while the agent waits?

E2B and Daytona bill reserved CPU and memory the whole time the sandbox is running. Modal bills the higher of the request and actual use, and the default request is 0.125 cores and 128 MiB. Vercel bills Active CPU only while the CPU is busy, and bills provisioned memory for the whole session, including model waits. Cloudflare Containers bill CPU on active use, and bill memory and disk for the chosen instance size until the container sleeps.

Which of these tools have an MCP server?

Daytona ships one in the CLI, started with daytona mcp start. Vercel hosts one at mcp.vercel.com with OAuth, and the docs include sandbox tools. Cloudflare hosts a Container server at containers.mcp.cloudflare.com/mcp that its catalog describes as spinning up a sandbox development environment. E2B runs an MCP gateway inside the sandbox so the agent can call other tools. Modal's docs show how to deploy an MCP server you write. They do not list a Modal-hosted server for creating sandboxes.

Can I run the sandbox on my own machines?

E2B documents E2B Embed, an Apache-2.0 package that runs the stack on one Linux machine you operate, plus bring-your-own-cloud. Daytona's June 11, 2026 post says the production code is private, and the old public repo is archived. Modal, Cloudflare, and Vercel run the machines. Their client SDKs are Apache-2.0.

Do I need a GPU sandbox?

Use a GPU when the code itself needs one, such as CUDA. E2B's pricing page says its sandboxes are CPU-only. Daytona and Modal both offer GPU sandboxes. A coding agent that edits a repository and runs tests usually needs CPU, memory, and a filesystem.
