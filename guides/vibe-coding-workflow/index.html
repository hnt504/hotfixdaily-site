Step 1: Plan before you prompt

Our take: write down the users, the one main flow, and how you'll know it works. Then hand that to the tool's planning mode.

Lovable Plan mode

Lovable's project chat has Chat, Plan and Build modes. In Plan mode, Lovable investigates and writes a plan you can edit and approve, and Lovable says Plan mode never modifies your code. It often asks clarifying questions first, and each Plan mode message costs one credit plus the cost of any subagent research.

Our take: Any change that touches several screens or your data model.

Source

Kiro specs

Kiro turns an idea into three files: requirements.md (user stories and acceptance criteria), design.md (technical architecture and sequence diagrams) and tasks.md (an implementation plan split into discrete tasks).

Our take: Writing a spec that any builder or agent can follow, even if you build somewhere else.

Source

Replit Plan mode

Replit's pricing page lists Plan mode in its Core plan ($20 a month, or $18 billed annually).

Our take: Replit users: plan first, then let Agent build.

Source

Step 2: Build the first version

Pick one builder (our vibe coding tools guide compares them) and build the smallest version of your main flow. Our take: ask for one screen or one flow per prompt. Big, vague prompts burn through credits and are harder to undo.

Lovable

Lovable hosts your app and includes a built-in backend with a database, authentication, storage, edge functions and AI.

Source

Bolt (affiliate)

Bolt's free plan includes 1M tokens a month (with a 300K daily limit), website hosting and unlimited databases. Pro is $18 a month billed annually and adds your own domain with no Bolt branding.

Source

v0 by Vercel

v0's free plan deploys apps to Vercel and syncs with GitHub, with a 7-message-a-day limit.

Source

Replit Agent

In Replit's words, Agent "sets up your project, creates applications, checks its work, and fixes problems along the way."

Source

Step 3: Add data and logins safely

Lovable Cloud (built-in backend)

Lovable's built-in backend gives you a database, real-time updates, user authentication, storage, edge functions, secrets and logs, with no separate setup. Lovable says it is built on Supabase's open-source foundation. You can also connect an external backend you set up yourself.

Our take: Non-developers who want logins and data without leaving the builder.

Source

Supabase Auth

Supabase Auth supports password, magic link, one-time password (OTP), social login and single sign-on (SSO).

Our take: Any builder or coding agent that uses Supabase as the backend.

Source

Row Level Security (the step people skip)

Supabase's docs put it plainly: a table in an exposed schema without RLS is readable and writable by any role with a grant on it, so enable RLS on every table in an exposed schema. They also warn that a policy reading to anon using ( true ) gives every unauthenticated visitor read access, so use it only for data that is meant to be public.

Our take: Before launch, ask your builder or agent to list every table and its RLS policies, and read that list yourself.

Source

Step 4: Get your code into GitHub

Our take: do this on day one, not when something breaks.

Lovable to GitHub

Lovable can export your project and keep it in two-way sync with github.com, GitHub Enterprise Cloud or GitHub Enterprise Server, for backup, collaboration and deployment. On paid plans you can also download the codebase directly.

Source

Bolt to GitHub

Connecting GitHub backs up your Bolt project with a full history of changes and syncs commits automatically. Each branch has its own memory. Because the code lives in GitHub, you can publish with Bolt hosting, the Netlify integration or another service.

Source

v0 to GitHub

A v0 chat connected to GitHub starts from the base branch you pick. When v0 has a change, it creates a working branch from that base and pushes there, and you ship through pull requests and CI.

Source

Moving between builders

Replit can import a GitHub repository, including projects exported from Lovable, Bolt or Base44, so GitHub sync also lets you change builders without starting over.

Source

Step 5: Keep building with a coding agent

When you need custom backend logic, keep hitting the builder's limits, or spend more on credits than a coding agent costs, open the GitHub repo in a coding agent. Our AI coding agents guide explains the options, and which AI coding agent to use compares prices.

AGENTS.md

An open format that its site calls "a README for agents": one place for the setup, build, test and code style commands that coding agents read. Add it to the repo before the agent's first task.

Our take: If the builder still syncs with the repo, have the agent work on a branch so the builder and the agent don't overwrite each other.

Source

Step 6: Test like a user

How to add these servers to your agent: see how to add MCP servers.

Playwright MCP

An MCP server that lets an agent drive a browser through Playwright using structured accessibility snapshots instead of screenshots. Microsoft notes that coding agents increasingly favor its Playwright CLI with skills because it uses fewer tokens, and keeps MCP for long-running, stateful browser sessions.

Our take: Having an agent click through sign-up, login, password reset and checkout on a preview URL.

Source

Chrome DevTools MCP

Gives coding agents control of a live Chrome browser for debugging: analyze network requests, check console messages, record performance traces and take screenshots.

Our take: Finding why a page is slow or why a request fails.

Source

Lovable security scans

Lovable has two built-in scans. The Quick scan runs automatically every time you publish and checks database access rules, dependencies and more. The Deep scan also reviews your application code and runs on demand. Lovable can auto-fix eligible findings, and says the scans do not replace a thorough security review.

Source

Step 7: Take payments (in a sandbox first)

Stripe sandboxes and test cards

In a Stripe sandbox, test card numbers simulate successful payments, declines, fraud, disputes, refunds and 3D Secure authentication, and no real money moves. You reach your sandboxes from the account picker in the Dashboard.

Our take: Test at least one decline and one refund before you switch to live keys, and keep the secret key in server-side secrets, never in front-end code.

Source

Step 8: Ship it

Our take: check every change on a preview URL before it goes to production. It's the cheapest safety net in this workflow.

v0 + Vercel

v0 deploys to Vercel. Working branches get preview deployments for review, and publishing updates production.

Source

Vercel from GitHub

Pushes get preview deployments, the production branch deploys to production, and Vercel offers instant rollback.

Source

Netlify

Deploy from Git, the CLI, drag and drop, or AI agents, with Deploy Previews for review.

Source

How to choose your path (our take)

  • Non-developer, simple app: Stay in one builder from step 1 to step 8. Use its backend, hosting and security scans, and still sync to GitHub.
  • Some coding, growing app: Build v1 in a builder, sync to GitHub by step 4, then do custom logic with a coding agent on a branch.
  • Developer prototyping: Use v0 or Bolt for the first UI, then move to your own repo, a coding agent and Vercel or Netlify previews.

Checklist before you ship

  • RLS is on for every table in an exposed schema, and you've read the policies yourself.
  • No secret keys in front-end code. They live in the builder's secrets or your host's environment variables.
  • Sign-up, login and password reset tested with a second account.
  • Payments tested in a Stripe sandbox, including a decline and a refund.
  • Code synced to GitHub, so you have history and a way out.
  • A security scan run, if your builder has one. More checks in our vibe coding tools guide.

Why: Supabase on Row Level Security

FAQ

What is a vibe coding workflow?

The steps for taking an app you built by describing it to an AI all the way to launch: plan, build, add data and logins, back up to GitHub, test, take payments and deploy. Vibe coding is fast at step 2. This workflow covers the other steps.

Can I ship a vibe-coded app to production?

Yes, if you review it like any other code. Supabase says to enable RLS on every table in an exposed schema, Stripe sandboxes let you test payments without real money, and preview deployments let you check each change before it goes live.

How do I get my code out of Lovable, Bolt or v0?

All three have GitHub integrations. Lovable has two-way sync, Bolt syncs commits automatically, and v0 pushes to a working branch that you merge through pull requests. Lovable's paid plans can also download the codebase.

When should I switch from a builder to a coding agent?

Our take: when you need custom backend logic, keep hitting the builder's limits, or spend more on credits than a coding agent subscription. Sync to GitHub first so you don't start over.

Do I need to know how to code?

Not for steps 1 to 4, or for step 8 on builder hosting. For steps 5 and 6 it helps to read diffs and test results, or to have someone who can.
