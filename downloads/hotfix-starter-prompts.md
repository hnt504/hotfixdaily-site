## 1. Kickoff: understand before touching  [Plan & build]

Use it: Start of any task in a codebase you (or the agent) don't know yet.

```text
Before writing any code, investigate and report back:
1. The files and functions involved in <feature/area>, with paths.
2. How data flows through them today, in 5 bullets max.
3. Existing tests that cover this area, and how to run just those.
4. Anything surprising or risky you noticed.
Don't edit anything yet.
```

## 2. Plan first  [Plan & build]

Use it: Any change bigger than a one-liner. Most bad agent output comes from skipping the plan.

```text
Task: <describe the outcome, not the implementation>.

Write a plan before coding:
- Goal in one sentence, and what "done" looks like from a user's point of view.
- Files you'll change or create, and why each one.
- Steps in order, each small enough to verify on its own.
- How you'll verify each step (test, command, or what to click).
- Open questions or assumptions. Mark any that are hard to undo.
Stop after the plan. I'll reply "go" or adjust it.
```

## 3. Small slice  [Plan & build]

Use it: After the plan is approved. Keeps each step reviewable.

```text
Do only step <n> of the plan. When it's done:
- Show `git diff --stat`.
- Run <test/typecheck command> and paste the result.
- Tell me how you verified the behavior.
Then stop. Don't start the next step.
```

## 4. Spec from a fuzzy idea  [Vibe coding]

Use it: Before your first prompt in Lovable, Bolt, v0, Replit or a coding agent.

```text
I want: <rough idea in plain words>.
Turn this into a one-page spec:
- User stories (max 5), each with acceptance criteria I can test by hand.
- What's explicitly out of scope for v1.
- Data the feature needs to store, as a table: field, type, who can read, who can write.
- Edge cases: empty state, errors, slow network, a user without permission.
Ask me up to 3 questions where my idea is ambiguous. Don't write code.
```

## 5. Launch-blocker review of an app you didn't write  [Vibe coding]

Use it: Before real users touch an app a builder tool generated.

```text
This app was generated by a builder tool and I'm about to put real users on it.
Give me a launch-blocker review:
1. Where auth happens, and any route or API that works without being signed in but shouldn't.
2. Every place data is read or written, and whether access is limited to the owner.
3. Every secret or API key, and whether any reach the browser.
4. What happens when the payment, email or AI provider is down.
Output: a list of blockers with file:line, then a list of "fix soon" items. Don't fix anything yet.
```

## 6. Review this diff  [Review]

Use it: Before you merge anything an agent wrote.

```text
Review the changes on this branch against <main>: run `git diff <main>...HEAD`.
Report findings as a table: severity (blocker / should fix / nit), file:line, problem, suggested fix.
Check for:
- Bugs: wrong conditions, off-by-one, null/undefined paths, unhandled promise or exception, race conditions.
- Behavior changes that the task didn't ask for.
- Missing tests for new branches of logic.
- Error handling that swallows errors or shows users raw error messages.
Only report real problems. If there are no blockers, say "No blockers" first.
Don't edit any files.
```

## 7. Reproduce first  [Debugging]

Use it: Something is broken. Stops the agent from guessing a fix.

```text
Bug: <what happens> when <steps>. Expected: <what should happen>.
Before changing any code:
1. Reproduce it. Write a failing test or a script that shows the bug, and run it. Paste the output.
2. If you can't reproduce it, tell me what you tried and what extra information you need. Don't guess a fix.
```

## 8. Find the cause, not a cause  [Debugging]

Use it: Right after the bug reproduces.

```text
The bug reproduces. Now find the root cause:
- Trace the path from <input/entry point> to <where it goes wrong>, with file:line for each hop.
- Add temporary logging if you need it, and show the actual values at each step.
- State the root cause in one sentence, and the evidence for it.
Then propose the smallest fix. Don't apply it yet.
```

## 9. When the agent goes in circles  [Debugging]

Use it: The third failed attempt at the same fix.

```text
Stop. You've tried <n> times and it's still failing.
Don't try another fix yet. Instead:
1. List every assumption you've been making about why this fails.
2. For each one, say how you could check it in one command or one log line.
3. Run those checks and report what's actually true.
Then propose one fix based on what you found.
```

## 10. The universal proof request  [Proof]

Use it: Paste this every time an agent says "done".

```text
Before I accept this, show proof:
1. The exact commands you ran to check it, and the last 20 lines of each output. Run them again now if you didn't keep the output.
2. `git status` and `git diff --stat`.
3. For each requirement in the task: done / not done / not verified, and the evidence for each.
If anything wasn't actually run, say "not verified". That's fine, I just need to know.
```

## 11. Session handoff  [Sessions]

Use it: End of a work session, so tomorrow's session (or another agent) can pick up cleanly.

```text
We're stopping here. Write a handoff note to `NOTES.md` (append, don't overwrite):
- What we were trying to do.
- What's done and verified, and how it was verified.
- What's in progress, with the exact file and function.
- What's broken or untested right now.
- The next 3 steps.
- Commands to get back to this state (branch, dev server, test command).
Keep it under 25 lines.
```

## 12. Gameplay change you can test in the editor  [Game dev]

Use it: Asking an agent to change a Godot or Unity game without breaking scenes.

```text
Engine: <Godot 4.x with GDScript | Unity <version> with C#>. Check this version before using any API.
Change: <the gameplay behavior you want, e.g. "double jump with a 0.2 s coyote time">.
Rules:
- Edit scripts only. Don't edit scene or prefab files (.tscn, .unity, .prefab) as raw text; describe any editor change and I'll make it.
- Put tunable values (speeds, timers, damage) in exported/serialized fields, not hard-coded numbers.
- No per-frame allocations in update loops; cache node and component lookups.
When done, tell me exactly how to test it: which scene to open, what input to press, and what I should see.
```

## 13. Tool-design review for your own agent  [Agent builders]

Use it: Before you give an LLM agent new tools or wire in outside content.

```text
Here are the tools my agent can call: <paste tool names, descriptions and parameter schemas>.
Review them as if you were the model using them:
1. For each tool: is the description clear enough to know when to call it and when not to? Rewrite any that are vague.
2. Which tools can change or delete things, spend money, or send messages? Mark each one "needs human approval" or "safe to auto-run", and say why.
3. Which tools return outside content (web pages, emails, files, user input)? For each, describe one prompt-injection attempt it could carry and how my code should contain it.
4. Any two tools that overlap and will confuse the model? Suggest a merge or a clearer split.
Output a table, then the rewritten descriptions. Don't change any code.
```
